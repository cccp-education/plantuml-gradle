== Contexte

Demande pilote (S-219) :

*« cadrer les epic pour le borough plantuml car son support au sein de document
n'est pas optimisé et doit être architecturé de manière à passer la chaîne de
transmission en douceur depuis bakery puis article vers document et en extraire
les plantuml dans le asciidoc pour que cela soit le borough plantuml qui en fasse
la traduction et la correction de syntaxe et alignement des dépendances
plantuml/asciidoc. »*

Déclencheur : le cadrage **CHE-DIAGRAM** (cheroliv.com S-068) a prouvé que les
diagrammes PlantUML rendent **blanc** au déploiement et que les variantes ne les
rendent **pas** — un symptôme dont la cause racine est **architecturale**: le
bloc PlantUML de l'article n'a **pas un propriétaire unique**.

Session de **gouvernance pure** (pattern S-057/S-063) : audit mesuré, décisions,
découpage en US. **Zéro code modifié.**

== Audit mesuré (S-219)

=== La chaîne réelle

[source]
----
bakery/runner (N3/N2, orchestration traduction arctique + bake)
        │  MigrateContentI18nTask.translateSingleFileWithBlockDelta
        ▼
document-gradle (N2)  DocumentTranslator
        │  AsciiDocParser → PivotBlock.Source(language="plantuml")
        │  PlantUmlTranslationAdapter  ← ⚠️ domaine PlantUML PRIVÉ à document
        │  AsciiDocRenderer / JbakeNativeRenderer
        ▼
bakery bake (asciidoctor-diagram, jbakeRuntime)  ← ⚠️ rendu SVG, version codée en dur
        ▼
cheroliv.com jbake/i18n/{lang}/…  (SVG généré au bake)
----

=== Constat C-1 — Split-brain du domaine de traduction

plantuml-gradle possède un **domaine Translation Boundary** complet (EPIC
PLT-BOUNDARY, S163-166, 8 US, ~26 pts) :

* `plantuml.boundary.TranslationResolver` — applique la stratégie
* `TextClassifier` — 3 natures (`PRESENTATION` / `SEMANTIC_IDENTITY` / `LEXICAL_FIELD`)
* `IdiomaticGlossary` + `NonTranslatableTermRegistry` — glossaire/registre YAML configurables
* `TranslationStrategy` enum — `TRANSLATE` / `BORROW` / `PRESERVE`
* `PlantumlTranslationServiceAdapter` — implémente le `TranslationService` N0

**document-gradle ne le consomme PAS.** `grep` à l'appui : **zéro import
`plantuml.boundary`** dans document. document réimplémente une version **plus
pauvre** :

|===
| plantuml (riche, inutilisé) | document (pauvre, actif)
| `TranslationCategory` (3 natures) | — (absent)
| `TranslationStrategy` (TRANSLATE/BORROW/PRESERVE) | `PlantUmlStrategy` (TranslateLabels/PreserveTechnical/BorrowVocabulary)
| `IdiomaticGlossary` (YAML) | — (absent)
| `NonTranslatableTermRegistry` (YAML) | — (absent)
| `TranslationResolver` (stratégie + glossaire) | `PlantUmlClassifier` + regex `"…"`
| `plantuml.validation.SyntaxValidationResult` standalone | `document.…PlantUmlValidationResult` (wrapper)
|===

Le domaine riche de plantuml est **mort pour le pipeline site** : la valeur
produite en S163-166 (26 pts) n'atteint jamais l'article.

=== Constat C-2 — La traduction de document casse la syntaxe PlantUML

`PlantUmlTranslationAdapter.translateLabels` remplace les labels par regex
`"([^"]+)"`. Or la traduction LLM restitue un **retour-ligne réel** là où la
source portait un échappement `\n` :

[source]
----
FR : rectangle "CLI de vibe coding\nOpen source, gratuit" as CLI
EN : rectangle "vibe coding CLI
     Open source, free" as CLI        ← saut de ligne réel
----

PlantUML échoue (`Syntax Error?`), asciidoctor-diagram **dégrade le bloc en
listing brut**. C'est exactement le défaut **D2 de CHE-DIAGRAM** (EN 0125 =
0 `<img>` / 5 `@startuml`). document valide *après* traduction
(`PlantUmlSyntaxValidator`) mais en mode `LENIENT` → **warn silencieux**, le bloc
cassé est publié.

=== Constat C-3 — Pas de contrat N0, couplage N2→N2

document déclare `implementation(libs.plantuml.plugin)` — une dépendance
**plugin-à-plugin** (N2→N2) pour n'utiliser que `PlantumlService.validateSyntax()`
+ `SyntaxValidationResult`. Le BACKLOG plantuml **anticipe déjà** l'extraction
d'un contrat N0 :

[quote]
----
Aujourd'hui le type standalone vit dans plantuml-plugin. Si d'autres boroughs
(codex, slider, bakery) ont besoin de valider du PlantUML sans dépendre du
plugin complet, un contrat N0 plantuml-validation-contracts pourra être extrait
dans le BOM.
----

=== Constat C-4 — Le rendu (toolchain) n'est pas gouverné

Le rendu `[plantuml] → SVG` est fait par asciidoctor-diagram dans bakery
(`SiteManager.createJBakeRuntimeConfiguration`, `jbakeRuntime`), avec des versions
**codées en dur** (`asciidoctorj-diagram:3.0.1` + `…-plantuml:1.2025.3`). Le BOM
publie `asciidoctorj-diagram:3.2.0` / `…-plantuml:1.2025.3` ; le runner force
`workspace-bom:0.0.65`. La version résolue en CI (**PlantUML 1.2026.0**) diffère
du local (**1.2026.2**) → **défaut D1 de CHE-DIAGRAM** (SVG `xmlns=''` → blanc).

Personne ne possède la version de la chaîne PlantUML : chaque maillon la
redécide.

=== Constat C-5 — Deux vocabulaires de stratégie divergents

`document.PlantUmlStrategy` (TranslateLabels/PreserveTechnical/BorrowVocabulary)
et `plantuml.boundary.TranslationStrategy` (TRANSLATE/BORROW/PRESERVE) décrivent
**la même décision sémantique** avec deux noms. Toute évolution doit être faite
deux fois — ou jamais.

=== Constat C-4 (affiné S-221) — Triple split-brain de version toolchain

L'audit US-5 a révélé que la version asciidoctor-diagram/plantuml n'a pas un
propriétaire, mais **trois sources divergentes** :

[cols="2,2,2"]
|===
| Source | asciidoctorj-diagram | asciidoctorj-diagram-plantuml
| `bakery.SiteManager` (hardcodé) | **3.0.1** | **1.2025.3**
| `bakery` toml local | 3.0.1 | 1.2026.2
| MEMPHIS BOM toml | **3.2.0** | 1.2025.3
|===

Le **classpath de bake** (`jbakeRuntime`, `SiteManager`) est une **liste
hardcodée** — il ignore à la fois le toml local, le catalogue `ws` et le BOM. La
version PlantUML **effectivement bakée** est celle **bundlée** dans
`asciidoctorj-diagram-plantuml` (`1.2025.3` → `plantuml-lgpl-1.2025.3`). **Cause
probable de D1** : le JAR standalone `net.sourceforge.plantuml:plantuml:1.2026.0`
(tiré transitivement via `document-plugin → plantuml-plugin`) **shadow** le
PlantUML bundlé sur ce classpath → une version de rendu non maîtrisée. US-5 doit
d'abord **prouver** ce shadowing (`dependencyInsight` sur la configuration de
bake), puis établir la **source unique** (catalogue `ws` consommé par
`SiteManager`) et une **garde** local↔CI.

**Indice supplémentaire (S-221)** : le bake **local** produit `<?plantuml 1.2026.2?>`
alors que `SiteManager` hardcode `1.2025.3` — donc le bake local **ne passe pas**
par cette liste hardcodée (il lit le toml bakery `1.2026.2`), tandis que la CI
produit `1.2026.0`. Trois mécanismes de résolution coexistent : il faut
**identifier lequel la CI emprunte** avant de gouverner la version.

**Preuve (S-221, `dependencyInsight` sur `bakery:runtimeClasspath`)** :

[source]
----
net.sourceforge.plantuml:plantuml:1.2026.0
\--- education.cccp:plantuml-plugin:0.0.5
     \--- education.cccp:document-plugin:0.0.20   (requested education.cccp:workspace-bom:0.0.65)
          \--- runtimeClasspath (requested education.cccp:document-plugin)
----

Le JAR **standalone** `net.sourceforge.plantuml:plantuml:1.2026.0` entre dans le
classpath de bakery **via `document-plugin → plantuml-plugin`** — il cohabite avec
le PlantUML **bundlé** dans `asciidoctorj-diagram-plantuml`. C'est la collision de
classes à arbitrer en US-5 (ordre de classpath / exclusion / source unique).


=== Synthèse — un bloc, cinq propriétaires de fait, zéro propriétaire de droit

|===
| Maillon | Qui code aujourd'hui | Devrait posséder
| Extraction du bloc `[plantuml]` | document (`AsciiDocParser`) | document (pivot AsciiDoc) ✅
| Modèle du bloc (`PlantUmlBlock`) | document (privé) | **plantuml** (contrat N0)
| Traduction des labels | document (regex pauvre) | **plantuml** (boundary riche)
| Validation syntaxique | document (wrapper) | **plantuml** (contrat N0)
| Version asciidoctor-diagram/plantuml | bakery (hardcodé) | **plantuml** (source unique)
| Rendu SVG | bakery/asciidoctor-diagram | bakery (mais version pilotée par plantuml)
|===

== Décisions

[cols="1,5"]
|===
| # | Décision

| D1
| **Le bloc PlantUML a un propriétaire : plantuml-gradle.** Le modèle, la
traduction, la validation et la **version du toolchain** appartiennent au
borough plantuml. document **extrait** le bloc et **délègue** ; il ne
réimplémente plus la logique PlantUML.

| D2
| **Contrat N0 `plantuml-contracts` (MEMPHIS).** Les types stables migrent du
plugin vers un artefact N0 minimal : `PlantUmlBlock`, `SyntaxValidationResult`,
`PlantUmlSyntaxValidator` (interface), `PlantUmlTranslationPort` (port de
traduction). document et bakery consomment le **contrat**, pas le plugin — fin
du couplage N2→N2 (C-3). Pattern des contrats existants
(`agent-contracts`, `i18n-contracts`, `ocr-contracts`).

| D3
| **Le port de traduction est implémenté par le domaine boundary de plantuml.**
| `PlantUmlTranslationPort` est le seul point d'entrée ; l'implémentation
réutilise `TranslationResolver` + `TextClassifier` + `IdiomaticGlossary` +
`NonTranslatableTermRegistry` (C-1) — la valeur S163-166 devient vivante.

| D4
| **Un seul vocabulaire de stratégie.** `document.PlantUmlStrategy` est
**supprimé** au profit de `TranslationStrategy` (TRANSLATE/BORROW/PRESERVE) du
contrat N0 (C-5). Un concept, un nom.

| D5
| **La traduction ne casse jamais la syntaxe (C-2).** Le port garantit qu'un
label traduit respecte l'échappement PlantUML (`\n` préservé) ; après
traduction, une **validation round-trip** (re-parse PlantUML) est obligatoire ;
un bloc invalide **n'est jamais publié** — soit il est **corrigé** (repli sur la
source), soit la stratégie est `PRESERVE`.

| D6
| **La version du toolchain est une donnée gouvernée.** plantuml-gradle
**expose** la version asciidoctor-diagram/plantuml de référence (attribut du
contrat ou constante publiée) ; bakery s'aligne dessus. Fin du drift
local↔CI (C-4, défaut D1 CHE-DIAGRAM).

| D7
| **La chaîne de transmission est explicite et testée de bout en bout.**
| Un scénario Cucumber traverse bakery → document → port → plantuml sur un
article réel à diagrammes, et vérifie : bloc extrait, labels traduits, syntaxe
valide, **rendu non blanc**.

| D8
| **Baby-step DDD/TDD/BDD strict** : RED (compile failure / assertion), GREEN,
REFACTOR ; unit → functional → cucumber. Aucune garde affaiblie.

| D9
| **Ordre DAG N0→N2 → N3.** Le contrat N0 est publié **avant** que document et
bakery le consomment. plantuml-plugin implémente le port ; la propagation BOM
suit l'ordre MEMPHIS → plantuml → document → bakery → runner.

| D10
| **Boundary** : plantuml possède le domaine + le contrat + la version ;
document possède l'extraction pivot AsciiDoc + le rendu AsciiDoc ; bakery
possède l'orchestration traduction + bake ; le rendu SVG reste dans le bake mais
sa version est pilotée par plantuml.

|===

=== Options écartées

* **Laisser document dupliquer (statu quo)** — deux vocabulaires, deux
traductions, la valeur PLT-BOUNDARY reste morte ; le bug `\n` persiste.
* **Faire porter le rendu SVG par plantuml-gradle** — contredit le bake
JBake/asciidoctor-diagram ; le rendu doit rester au bake, seule sa **version**
est gouvernée.
* **document dépend du plugin complet** (sans contrat N0) — conserve la dette
N2→N2 et expose toute l'API du plugin ; le contrat N0 est le remède prévu par
le BACKLOG.
* **Contrat N0 dans `workspace-bom` monolithe** — non : artefact standalone
comme `ocr-contracts`/`runtime-contracts`.
