== 0. Objet & méthode

Le borough plantuml (HTOWN) génère, valide et traduit des diagrammes PlantUML via
LLM (`DiagramProcessor` + `LlmService` + `PlantumlService` + RAG). `diag-agent`
(docToolchain, MIT, ~107 commits) est un agent LLM de génération de diagrammes
d'architecture dont le cœur est une **boucle d'auto-validation** (génération →
validation → raffinement), étendue par une **validation de description** en amont et
un **retour design par vision** en aval.

*Méthode* : clone `git clone --depth 1 https://github.com/docToolchain/diag-agent`
dans un répertoire temporaire (`/tmp/opencode/diag-agent`) — **lecture seule** ;
HEAD `45068441bf9ea13b430168f9b81f700803ca0386` (2025-12-17). Analyse des 9 modules
de `src/diag_agent` + ADR arc42 + `pyproject.toml` + `tests/`. Comparaison au code
réel de HTOWN (lecture seule) pour ne proposer que des **capacités manquantes**.

*Règle de lecture* : chaque item porte *objectif*, *domaine pur*, *port/adapter*,
*tâche Gradle*, *opt-in*, *tests* (unit → functional → cucumber), *points*. Toute
option est **opt-in (défaut `false`)**, câblée sur les **4 sources de config**
(ENV / gradle.properties / YAML / CLI) + `pushConfigIntoExtension`, et n'est jamais un
prérequis de `check`.

== 2. Code review — forces (ce qui a de la valeur)

. **Boucle d'auto-validation ancrée sur un oracle de rendu.** `Orchestrator.execute`
  (`orchestrator.py:347-403`) rend le diagramme via Kroki en SVG ; une erreur de rendu
  (`KrokiRenderError`) est **réinjectée telle quelle** dans le prompt de correction
  suivant (`orchestrator.py:325`). Le verdict est binaire et *extérieur* au LLM.
. **Pré-vol de description** (`LLMClient.validate_description`, `client.py:148-218`).
  Avant génération, un LLM vérifie complétude/cohérence/clarté et renvoie des
  **questions de clarification**. **Fail-safe** : toute erreur → considéré valide.
. **Retour design par vision** (`client.py:94-146` + `orchestrator.py:359-391`). Le
  diagramme rendu en PNG est **analysé par un modèle vision** (mise en page /
  lisibilité / espacement), jusqu'à « approved ». Seul mécanisme qui capte ce que la
  validation de syntaxe **ne voit pas**.
. **Budget borné** : double garde `max_iterations` et `max_time_seconds`
  (`orchestrator.py:301-320`), avec `stopped_reason` (`success` / `max_iterations` /
  `max_time`).
. **Bibliothèque d'exemples few-shot** (`orchestrator.py:159-215`) : exemples
  canoniques par type/sous-type injectés dans le prompt (au-delà du RAG).
. **Détection de sous-type** (`orchestrator.py:129-157`) pour choisir exemplaire et
  template (context/container/component ; sequence/activity/class…).
. **Local-first + dégradation** (ADR-003/006) : Kroki Docker par défaut, fallback
  remote en mode auto, mode local strict.
. **Journal d'exécution** `generation.log` par run.

[cols="1,2,7,1", options="header"]
|===
| # | Sévérité | Constat | Réf.

| C-1 | 🔴 | **`sys.exit(1)` dans une classe d'orchestration** — couplage bibliothèque↔CLI. En mode **MCP**, `mcp/server.create_diagram` appelle `execute()` sans `skip_validation` : une description invalide **tue le serveur MCP**. Bug réel, non testé. | `orchestrator.py:286`, `mcp/server.py:53`
| C-2 | 🔴 | **Messages utilisateur allemands codés en dur** dans la couche d'orchestration (`"Die Beschreibung enthält Unklarheiten"`). | `orchestrator.py:279-282`
| C-3 | 🟠 | **Pas de port/adapter** : `Orchestrator` instancie `LLMClient`/`KrokiClient` en dur ; `litellm.completion`/`httpx.post` statiques → pas de seam d'injection. | `orchestrator.py:36-40`, `client.py:71`

|===

=== Ce qu'il ne faut PAS porter

* `sys.exit` dans une couche non-CLI (C-1) — HTOWN = plugin Gradle → `GradleException`.
* Messages hardcodés (C-2) — HTOWN a `PlantumlMessages` i18n (10 langues).
* Sortie `diagram.<ext>` (C-7) — HTOWN **dérive déjà** le nom du prompt.
* Logger module global muté (C-9) — préférer le logger de tâche Gradle.
* Kroki comme oracle — HTOWN valide **nativement** (`SourceStringReader`, hors-ligne).

== 7. Décisions d'architecture

. **Domaine `plantuml.agent` (nouveau, N2).** Objets purs d'abord (parsables,
  hors I/O, unit-testables), ports/adapter ensuite. Aucune dépendance réseau dans
  le domaine.
. **La boucle reste dans `DiagramProcessor`.** On **étend** la boucle existante
  (déjà correcte et couverte) plutôt que d'en écrire une seconde (anti-pattern C-5).
. **Aucun nouveau moteur de rendu.** La validation reste **native** (hors-ligne).
  Kroki n'est **pas** porté (seul le multi-format, déjà couvert par asciidoctor-diagram).
4.  **Vision = opt-in et dégradable.** Un modèle sans capacité vision → revue
  **sautée**, jamais un échec de build. La revue design ne bloque pas `check`.
. **Réutiliser `LlmService`/`ChatModel`** (port existant) — pas de couplage direct.
. **4 sources + `pushConfigIntoExtension`** pour chaque option (`maxSeconds`,
  `designValidation`, `preflight`), défaut `false`/`0` (backward compat).
. **i18n** : toute chaîne utilisateur via `PlantumlMessages` (10 langues).
. **Économie d'Encre** : DIA-07 arrête le brûlage d'appels identiques ; DIA-01 ne
  relance la revue que si la source a changé.
. **English only** (code, Gherkin, tests) ; gouvernance `.adoc` en français.
