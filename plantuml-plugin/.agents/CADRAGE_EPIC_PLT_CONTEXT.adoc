_Question pilote (S-231) : la génération de diagrammes PlantUML devrait être confiée
à un **contrat qui travaille avec codebase** pour apporter un **contexte augmenté**
(RAG/Graphify/Docs/EAGER). Est-ce déjà le cas ? Sinon, cadrer un EPIC dans
plantuml-plugin. **Gouvernance pure — zéro code modifié.**_

== 0. Réponse courte

**Non, ce n'est pas le cas.** plantuml **applique** le plugin `education.cccp.codebase`
(`build.gradle.kts:26`) mais n'importe **aucun** type `codebase.*` ; il possède son
propre « RAG » **statique** (`DocKnowledgeBase`, recherche par mots-clés sur une
ressource embarquée) et n'expose/consomme **aucun** contrat de contexte
(`contracts.context.*`). C'est le **retardataire** cross-borough : capsule, planner et
slider consomment déjà le hub N1. → **Oui, l'EPIC `PLT-CONTEXT` est fondé.**

== 3. Décision — EPIC `PLT-CONTEXT`

*Objet* : confier le **contexte augmenté de génération** de plantuml au **contrat N0
`contracts.context.*`** (codebase-contracts) alimenté par le socle **N1 codebase**, en
suivant le patron capsule — au lieu du `DocKnowledgeBase` statique.

*Frontière (DAG)* : le **contrat** est N0 (`codebase-contracts`, provider-agnostique) ;
le **moteur** est N1 (codebase). plantuml **ne dépend jamais d'un autre N2** (codex).
Le `DocKnowledgeBase` statique est **conservé en repli** (dégradation hors-ligne, quand
aucun canal n'est fourni).

*Priorité* : 🟠 HAUTE — aligne plantuml sur l'architecture « contexte augmenté » et
remplace un RAG jouet par le socle partagé (qualité de génération + anti-hallucination).

*Charge* : ~13 pts (5 items + BDD).

== 4. Non-régression (charte, opposable à chaque US)

* **Validation native hors-ligne** (`PlantumlService`) et **boucle** `DiagramProcessor`
  (récemment enrichie par `PLT-AGENT`) : **inchangées**.
* **Multi-provider + pool + fallback** (`LlmService`) : préservé (sauf arbitrage CTX-05).
* **i18n** 10 langues (`PlantumlMessages`), **toolchain gouvernée** (`PlantUmlToolchain`),
  **probe anti-blanc**, **incrémentalité** + **Économie d'Encre**, **contrats N0** déjà
  consommés (`plantuml-contracts`, `i18n-contracts`) : préservés.
* **Dégradation** : sans contexte (ou hors-ligne), la génération fonctionne comme
  aujourd'hui (repli `DocKnowledgeBase`).

== 6. Décisions

. **D-1 — Contrat = N0.** Le seam est `contracts.context.*` (`codebase-contracts`),

. **D-2 — Patron capsule.** Assembleur **pur** (CTX-02) + **collecteur** Gradle (CTX-03) ;
  réutilise `ContextChannel`/`ChannelBudget` (budget 8000, 40/30/20/10).

. **D-4 — Économie d'Encre.** L'artefact `augmented-context.txt` est réutilisé ;
  invalidation ciblée (fichiers source changés), jamais globale.
. **D-5 — `LlmBuildService` : CADUQUE (arbitrage S-232).** On **ne remplace pas** le
  `LlmService` local par le hub N1 (le local est un superset ; le hub est Ollama-centré ;
  les adopter tous deux = split-brain). Voir § 11.
. **D-6 — Provenance.** Le collecteur émet la traçabilité (anti-hallucination), comme
  capsule (`CAP-PROVENANCE`).
. **D-7 — English only, 4 sources, défaut off** pour toute nouvelle option.
. **D-8 — Local = Build, Tests = CI** ; appel LLM en CI = Ollama caché (`setup-ollama`)
  ou **mock**.

== 11. Arbitrage CTX-05 — VERDICT : **CADUQUE** (S-232)

_Question : remplacer le `LlmService` local de plantuml par le hub N1
`codebase.koog.llm.service.LlmBuildService` (consommé par slider/planner/capsule) ?_

=== Ce que chaque moteur couvre réellement

[cols="2,3,3", options="header"]
|===
| Critère | `LlmBuildService` (N1 codebase) | `LlmService` (N2 plantuml)

| Portée | résolution **1 provider** (`LlmServiceResolver.resolveProvider(model)`) + **pool Ollama local** (`OllamaPool`/`OllamaInstanceScanner`, `RotationStrategy.ROUND_ROBIN`) | **7 providers** (ollama/openai/gemini/mistral/claude/huggingface/groq)
| Pool / rotation | pool **Ollama par ports** (instances locales) | `ApiKeyPool` (ROUND_ROBIN + **tiered**), `QuotaTracker`/`QuotaResetManager`, **`CrossProviderFallbackOrchestrator`**, `FreemiumWeightCalculator`, `QuotaAuditLogger`
| Modèles par provider | provider-level | `ProviderModelResolver` (par provider)
| DI | **Gradle `BuildService`** (partagé, cycle de vie Gradle) | instanciation directe par tâche
| Test | mock via `-Pollama.baseUrl` | `plantuml.test.mode` → `null`
|===

=== Pourquoi le remplacement est rejeté

. **Superset.** `LlmService` couvre **plus** que le hub (7 providers + pool de clés API +
  quota + fallback cross-provider + audit + poids freemium). Le remplacer serait une
  **régression** — violation de la charte de non-régression (§ 4).
. **Le hub est Ollama-centré.** Son pool est une **rotation par ports** d'instances
  locales ; il ne porte **pas** le pool de **clés API cloud** dont plantuml a besoin.
. **Split-brain.** Adopter les deux (hub pour Ollama, `LlmService` pour le cloud) crée
  **deux chemins de résolution LLM** = l'anti-pattern que le workspace combat
  (`WORKSPACE_AS_PRODUCT.adoc`).
. **Gains additifs mineurs.** Le seul apport réel (DI `BuildService` + rotation de ports
  Ollama) est **petit** et réalisable **côté plantuml** (envelopper `LlmService` en
  `BuildService`, ajouter une rotation de ports) **sans** adopter le hub.

=== Conséquence

* **CTX-05 = CADUQUE.** On **ne remplace pas** `LlmService`. `PLT-CONTEXT` se réduit à
  `CTX-01`→`CTX-04` (le contexte augmenté — la vraie valeur) : **~10 pts**.
* **Porte ouverte (hors périmètre plantuml).** Une **convergence LLM cross-borough**
  (unifier le socle LLM dans codebase N1, avec pool de clés API cloud) serait un **EPIC
  N1 codebase**, pas une décision plantuml — à arbitrer par le pilote si la parité devient
  un objectif.
* *Item futur optionnel plantuml* (non requis) : envelopper `LlmService` en `BuildService`
  (DI) + rotation de ports Ollama — additif, sans adopter le hub.
